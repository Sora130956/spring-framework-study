# Classpath Scanning — Filters, Naming, Scopes, Qualifier Metadata & @Bean in Components

> **来源:** https://docs.spring.io/spring-framework/reference/core/beans/classpath-scanning.html

## 核心理解

Classpath scanning 是 Spring 取代 XML 配置的核心机制——通过 `@ComponentScan` 自动扫描 classpath 下的 stereotype 注解类并注册为 Bean。本笔记聚焦该页面后半部分的 5 个进阶话题：自定义扫描过滤器、自动检测 Bean 的命名规则、作用域配置、Qualifier 元数据注入方式，以及 `@Component` 内定义 `@Bean` 方法的特殊行为。

最关键的两个精读 section（实用 >= 7）是 **Naming Autodetected Components**（命名规则 + Spring 6.1 的 `@AliasFor` 变化影响实际开发）和 **Scope for Autodetected Components**（`@Scope` 的继承限制 + scoped proxy 选择——这两个在日常写代码时极易踩坑）。其余三个 section 属于"知道有这个东西，用到再查"的级别。

## 关键点

### Using Filters to Customize Scanning

> By default, classes annotated with @Component, @Repository, @Service, @Controller, @Configuration, or a custom annotation that itself is annotated with @Component are the only detected candidate components. However, you can modify and extend this behavior by applying custom filters. Add them as includeFilters or excludeFilters attributes of the @ComponentScan annotation.

默认情况下，只有标注了 `@Component`、`@Repository`、`@Service`、`@Controller`、`@Configuration` 或自定义的 `@Component` 派生注解的类才会被扫描到。通过 `includeFilters` 和 `excludeFilters` 可以扩展或缩小这个范围。

**五种 Filter 类型：**

| Filter Type | 匹配逻辑 | 典型场景 |
|-------------|---------|---------|
| `annotation` (默认) | 类上是否标注了指定注解（含元注解） | 排除所有 `@Repository`：`excludeFilters = @Filter(Repository.class)` |
| `assignable` | 类是否实现了指定接口或继承了指定类 | 只扫描某接口的实现类 |
| `aspectj` | 使用 AspectJ 类型表达式匹配 | `org.example..*Service+` 匹配所有 Service 及其子类 |
| `regex` | 正则匹配全限定类名 | `.*Stub.*Repository` 匹配含 Stub 的 Repository |
| `custom` | 实现 `TypeFilter` 接口，自定义逻辑 | 按类上是否有特定方法/注解组合过滤 |

```java
@Configuration
@ComponentScan(basePackages = "org.example",
    includeFilters = @Filter(type = FilterType.REGEX, pattern = ".*Stub.*Repository"),
    excludeFilters = @Filter(Repository.class))
public class AppConfig { }
```

> You can also disable the default filters by setting useDefaultFilters=false on the annotation. This effectively disables automatic detection of classes annotated or meta-annotated with @Component, @Repository, @Service, @Controller, @RestController, or @Configuration.

设置 `useDefaultFilters = false` 可以关闭默认的 stereotype 检测，此时只扫描 `includeFilters` 明确指定的类。

### Naming Autodetected Components

> When a component is autodetected as part of the scanning process, its bean name is generated by the BeanNameGenerator strategy known to that scanner. By default, the AnnotationBeanNameGenerator is used. For Spring stereotype annotations, if you supply a name via the annotation's value attribute that name will be used as the name in the corresponding bean definition.

自动检测的组件，Bean 名称由 `BeanNameGenerator` 策略生成。默认使用 `AnnotationBeanNameGenerator`：
- 如果注解的 `value` 属性有值（如 `@Service("myMovieLister")`），则该值为 Bean 名
- 如果没有显式指定，取类名首字母小写（`MovieFinderImpl` → `movieFinderImpl`）

```java
@Service("myMovieLister")    // Bean 名: myMovieLister
public class SimpleMovieLister { }

@Repository                 // Bean 名: movieFinderImpl（自动生成）
public class MovieFinderImpl implements MovieFinder { }
```

> As of Spring Framework 6.1, the name of the annotation attribute that is used to specify the bean name is no longer required to be value. Custom stereotype annotations can declare an attribute with a different name (such as name) and annotate that attribute with @AliasFor(annotation = Component.class, attribute = "value").

Spring 6.1 起，自定义构造型注解可以通过 `@AliasFor` 将非 `value` 的属性映射到 `@Component` 的 `value`：

```java
@Target(ElementType.TYPE)
@Retention(RetentionPolicy.RUNTIME)
@Documented
@Component // 继承 @Component 元注解，使其成为 Spring 构造型注解
public @interface MyComponent {

    // 核心：定义 "name" 属性（而不是常规的 "value"），通过 @AliasFor 桥接到 @Component.value
    @AliasFor(annotation = Component.class, attribute = "value")
    String name() default "";
}
```

> **使用方式：** `@MyComponent(name = "myBean")` → Bean 名 = `"myBean"`

> As of Spring Framework 6.1, support for convention-based stereotype names is deprecated and will be removed in a future version of the framework. Consequently, custom stereotype annotations must use @AliasFor to declare an explicit alias for the value attribute in @Component.

**Spring 6.1 之后：** 自定义构造型注解如果想让 Bean 有自定义名称，**必须**通过 `@AliasFor` 显式声明对 `@Component.value` 的别名，旧式基于约定的命名方式已弃用。

**这影响 Spring 标准注解吗？不影响。** `@Component`、`@Service`、`@Repository`、`@Controller` 等标准注解内部已经妥善处理了 `value` 属性与 `@Component` 的元注解关系，`@Service("userService")` 的使用方式没有任何改变。

> If you do not want to rely on the default bean-naming strategy, you can provide a custom bean-naming strategy. First, implement either the BeanNameGenerator or ConfigurationBeanNameGenerator interface, and be sure to include a default no-arg constructor.

自定义 `BeanNameGenerator` 时**必须有无参构造器**——因为它在容器启动早期通过反射实例化，此时依赖注入尚未就绪，无法解析构造器参数。

```java
@Configuration
@ComponentScan(basePackages = "org.example", nameGenerator = MyNameGenerator.class)
public class AppConfig { }
```

> If you run into naming conflicts due to multiple autodetected components having the same non-qualified class name (for example, classes with identical names but residing in different packages), you can configure a BeanNameGenerator that defaults to the fully-qualified class name for the generated bean name. The FullyQualifiedAnnotationBeanNameGenerator can be used for such purposes.

一个实际应用场景：当不同包下有同名的类（如 `com.a.ServiceImpl` 和 `com.b.ServiceImpl`），默认的短类名策略会产生冲突。使用 `FullyQualifiedAnnotationBeanNameGenerator` 可以自动生成全限定名作为 Bean 名，如 `com.example.MyConfig.myBean`。

> As a general rule, consider specifying the name with the annotation whenever other components may be making explicit references to it. On the other hand, the auto-generated names are adequate whenever the container is responsible for wiring.

**实践经验：** 如果一个 Bean 会被 `@Qualifier`、`@Resource(name = ...)` 或 `getBean("...")` 按名称引用——给它一个明确的名字（`@Component("myBean")`）。如果只是靠 `@Autowired` 按类型装配，默认名就够用。

### Providing a Scope for Autodetected Components

> As with Spring-managed components in general, the default and most common scope for autodetected components is singleton. However, sometimes you need a different scope that can be specified by the @Scope annotation.

默认作用域是 singleton，可以通过 `@Scope` 指定其他作用域：

```java
@Scope("prototype")
@Repository
public class MovieFinderImpl implements MovieFinder { }
```

> @Scope annotations are only introspected on the concrete bean class (for annotated components) or the factory method (for @Bean methods). In contrast to XML bean definitions, there is no notion of bean definition inheritance, and inheritance hierarchies at the class level are irrelevant for metadata purposes.

**关键限制：`@Scope` 不会被子类继承。** 在父类上写 `@Scope("prototype")`，子类不会自动变成 prototype——始终是默认的 singleton。

```java
@Scope("prototype")
public abstract class BaseService { }

@Component
public class UserService extends BaseService { }  // ❌ 实际是 singleton，不是 prototype！
```

这是因为注解方式的 Bean 定义没有 XML 那种"Bean 定义继承"机制。只有 XML 的 `<bean parent="...">` 才支持 scope 继承。

> When using certain non-singleton scopes, it may be necessary to generate proxies for the scoped objects.

非单例 Bean（如 prototype、request、session）被注入到单例 Bean 时，如果不做代理处理，单例 Bean 只会在初始化时获得一个实例，之后不会再获取新实例。解决方式是使用 **AOP 代理**：注入的是代理对象，每次方法调用时代理去容器获取新的目标实例。

**两种 ScopedProxyMode：**

| Mode | 代理方式 | 要求 |
|------|---------|------|
| `ScopedProxyMode.INTERFACES` | JDK 动态代理（基于接口） | 目标类必须实现至少一个接口 |
| `ScopedProxyMode.TARGET_CLASS` | CGLIB 子类代理 | 类不能是 final，方法不能是 final |

```java
@Configuration
@ComponentScan(basePackages = "org.example", scopedProxy = ScopedProxyMode.INTERFACES)
public class AppConfig { }
```

- `INTERFACES` 下注入时用接口类型接收（`@Autowired private UserService userService`，其中 `UserService` 是接口）
- `TARGET_CLASS` 下注入时可以用具体类类型接收
- 如果选了 `INTERFACES` 但目标类没实现任何接口 → `BeanCreationException`

### Providing Qualifier Metadata with Annotations

> @Qualifier("Action")

`@Component("beanName")` 和 `@Qualifier("category")` 的区别：
- `@Component("beanName")` → 给 Bean 起唯一名字（身份证号）
- `@Qualifier("category")` → 给 Bean 打分类标签（属于哪一类）

在 classpath scanning 下，Qualifier 元数据直接写在类级别注解上即可，不再需要在 XML 里配置 `<qualifier>` 子元素。

### Defining Bean Metadata within Components

**核心结论：** `@Component` 里的 `@Bean` 方法确实能注册 Bean，但和 `@Configuration` 里的 `@Bean` 有本质区别。

| | `@Configuration` | `@Component` |
|---|---|---|
| `@Bean` 方法相互调用 | 走 CGLIB 代理，单例语义不变 ✅ | 普通 Java 方法调用，可能破坏单例 ❌ |
| CGLIB 增强 | ✅ 有 | ❌ 无 |
| 适用场景 | **首选**，常规 Bean 定义 | 极其冷门，仅在特殊场景（利用类的继承能力批量生产 Bean） |

**结论：绝大多数情况下不应该在 `@Component` 里用 `@Bean`。** 能用 `@Configuration` 就用配置类，普通组件用 `@Component` + `@Autowired` 就够了。

## 句子解析

### 原文: "@Scope annotations are only introspected on the concrete bean class (for annotated components) or the factory method (for @Bean methods). In contrast to XML bean definitions, there is no notion of bean definition inheritance, and inheritance hierarchies at the class level are irrelevant for metadata purposes."

- **翻译:** @Scope 注解仅在具体的 Bean 类上（针对注解组件）或工厂方法上（针对 @Bean 方法）被解析。与 XML Bean 定义不同，这里不存在 Bean 定义继承的概念，类级别的继承体系在元数据层面是无关的。
- **解析:** `are only introspected on` 是被动语态，"仅在...上被解析/内省"。`there is no notion of` = "不存在...的概念"。`irrelevant for` 这个表达很精准——不是说父类不存在，而是说"不相关、不会被考虑"。

### 原文: "When using certain non-singleton scopes, it may be necessary to generate proxies for the scoped objects."

- **翻译:** 当使用某些非单例作用域时，可能需要为这些作用域对象生成代理。
- **解析:** `it may be necessary to` 是委婉表达客观必要性的句式，比 `you must` 更正式、更文档化。`scoped objects` = "具有作用域的对象"，这里 `scoped` 是过去分词作形容词。
